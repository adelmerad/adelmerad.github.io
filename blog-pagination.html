Why the last page is slow: cursor pagination in practice Pourquoi la dernière page est lente : la pagination par curseur en pratiqueلماذا تكون الصفحة الأخيرة بطيئة: الترقيم بالمؤشر عملياً

OFFSET pagination gets slower with every page and repeats rows when new data arrives. I measured both problems on a million rows, then looked at how our mission log API and its React frontend handled pagination, including what we got wrong. La pagination avec OFFSET ralentit à chaque page et répète des lignes quand de nouvelles données arrivent. J'ai mesuré ces deux problèmes sur un million de lignes, puis regardé comment l'API de notre journal de missions et son frontend React gèrent la pagination, y compris ce que nous avions mal fait.الترقيم باستعمال OFFSET يصبح أبطأ مع كل صفحة، ويكرّر الأسطر عندما تصل بيانات جديدة. قست هاتين المشكلتين على مليون سطر، ثم نظرت كيف تتعامل واجهة سجل المهام البرمجية وواجهتها الأمامية بـ React مع الترقيم، بما في ذلك ما أخطأنا فيه.

The projectLe projetالمشروع

Our team of three studied pagination as a data-access strategy, with a working example: the mission log of Rifters, an augmented reality game concept about Algerian history. Every completed mission is stored with its era, place and date, and the log can grow long. A Django REST API serves 300 seeded missions, and a React page loads them as you scroll. I built the frontend. Notre équipe de trois a étudié la pagination comme une stratégie d'accès aux données, avec un exemple concret : le journal de missions de Rifters, un concept de jeu en réalité augmentée sur l'histoire de l'Algérie. Chaque mission terminée est enregistrée avec son époque, son lieu et sa date, et le journal peut devenir long. Une API Django REST sert 300 missions générées, et une page React les charge au fil du défilement. J'ai construit le frontend.درس فريقنا المكوّن من ثلاثة أشخاص الترقيم كاستراتيجية للوصول إلى البيانات، مع مثال عملي: سجل المهام في Rifters، وهو تصور للعبة واقع معزّز عن تاريخ الجزائر. تُخزَّن كل مهمة منجزة مع حقبتها ومكانها وتاريخها، وقد يطول السجل كثيراً. تقدّم واجهة Django REST البرمجية 300 مهمة مولّدة، وتحمّلها صفحة React أثناء التمرير. وأنا من بنى الواجهة الأمامية.

OFFSET and its two problemsOFFSET et ses deux problèmesOFFSET ومشكلتاه

The usual way to paginate is to skip rows: La façon habituelle de paginer, c'est de sauter des lignes :الطريقة المعتادة للترقيم هي تخطي الأسطر:

SELECT * FROM mission ORDER BY visited_at DESC LIMIT 10 OFFSET 500000;

It is simple and allows "go to page 50,000". But the database cannot jump to row 500,000: it walks through the first 500,000 rows and throws them away. And the pages are defined by position, so if a row is added at the top between two requests, everything shifts by one. C'est simple, et ça permet « aller à la page 50 000 ». Mais la base de données ne peut pas sauter directement à la ligne 500 000 : elle parcourt les 500 000 premières lignes et les jette. Et les pages sont définies par position : si une ligne est ajoutée en haut entre deux requêtes, tout se décale d'une ligne.إنها بسيطة، وتسمح بـ«الانتقال إلى الصفحة 50,000». لكن قاعدة البيانات لا تستطيع القفز مباشرة إلى السطر 500,000: فهي تمرّ على الأسطر الـ500,000 الأولى ثم ترميها. كما أن الصفحات معرَّفة بالموضع، فإذا أُضيف سطر في الأعلى بين طلبين، انزاح كل شيء بسطر واحد.

A cursor (or "keyset") replaces the position with a value: "give me the 10 missions completed before the last one I saw". Un curseur (ou « keyset ») remplace la position par une valeur : « donne-moi les 10 missions terminées avant la dernière que j'ai vue ».أما المؤشر (cursor أو «keyset») فيستبدل الموضع بقيمة: «أعطني المهام العشر التي أُنجزت قبل آخر مهمة رأيتها».

SELECT * FROM mission
WHERE (visited_at, id) < ('2025-03-14 10:21:07', 418)
ORDER BY visited_at DESC, id DESC
LIMIT 10;

With an index on (visited_at, id), the database goes straight to that point in the index and reads 10 entries. The id breaks ties when two missions share the same date. Avec un index sur (visited_at, id), la base de données va directement à ce point de l'index et lit 10 entrées. L'id départage deux missions qui ont la même date.مع فهرس على (visited_at, id)، تذهب قاعدة البيانات مباشرة إلى تلك النقطة في الفهرس وتقرأ 10 مدخلات. ويفصل id بين مهمتين لهما التاريخ نفسه.

Both return exactly the same rows: J'ai rempli un fichier SQLite avec 1 000 000 de missions, indexées sur (visited_at DESC, id DESC), et j'ai lu une page de 10 lignes complètes à différentes profondeurs avec les deux méthodes (médiane de 5 essais, sur mon ordinateur). Les deux renvoient exactement les mêmes lignes :ملأت ملف قاعدة بيانات SQLite بـ 1,000,000 مهمة، مفهرسة على (visited_at DESC, id DESC)، وجلبت صفحة من 10 أسطر كاملة على أعماق مختلفة بالطريقتين (وسيط 5 محاولات، على حاسوبي). وكلتاهما تُرجعان الأسطر نفسها تماماً:

OFFSET grows with the depth: the last page is about 1,000 times slower than with a cursor, which stays flat. The query plans say why: OFFSET is a SCAN of the index, the cursor a SEARCH. Sixty milliseconds looks small, but it is per request, on every request to a deep page, and it keeps growing with the table. OFFSET grandit avec la profondeur : la dernière page est environ 1 000 fois plus lente qu'avec un curseur, qui reste constant. Les plans de requête disent pourquoi : OFFSET fait un SCAN de l'index, le curseur un SEARCH. Soixante millisecondes, ça paraît peu, mais c'est par requête, pour chaque requête vers une page profonde, et ça continue de grandir avec la table.يكبر OFFSET مع العمق: الصفحة الأخيرة أبطأ بنحو 1,000 مرة مقارنة بالمؤشر، الذي يبقى ثابتاً. وتوضح خطط الاستعلام السبب: OFFSET يقوم بـ SCAN للفهرس، والمؤشر بـ SEARCH. ستون جزءاً من الألف من الثانية تبدو قليلة، لكنها لكل طلب، ولكل طلب نحو صفحة عميقة، وتواصل النمو مع الجدول.

The row that appears twiceLa ligne qui apparaît deux foisالسطر الذي يظهر مرتين

The second problem is about correctness. With pages of 3, newest first, I loaded page 1, then added a new mission, then loaded page 2: Le deuxième problème concerne l'exactitude. Avec des pages de 3, les plus récentes d'abord, j'ai chargé la page 1, puis ajouté une nouvelle mission, puis chargé la page 2 :المشكلة الثانية تتعلق بالصحة. بصفحات من 3، الأحدث أولاً، حمّلت الصفحة 1، ثم أضفت مهمة جديدة، ثم حمّلت الصفحة 2:

MissionsMissionsالمهام

The new mission pushed mission 3 to position 4, so OFFSET showed it again. In an infinite scroll, that is a duplicated card; when rows are deleted, it is a card the user never sees. The cursor does not care: "before mission 3" means the same thing whatever happened at the top. La nouvelle mission a poussé la mission 3 en position 4, donc OFFSET l'a montrée une deuxième fois. Dans un défilement infini, c'est une carte en double ; quand des lignes sont supprimées, c'est une carte que l'utilisateur ne voit jamais. Le curseur s'en moque : « avant la mission 3 » veut dire la même chose, quoi qu'il se soit passé en haut.دفعت المهمة الجديدة المهمة 3 إلى الموضع 4، فأظهرها OFFSET مرة ثانية. في التمرير اللانهائي، هذه بطاقة مكررة؛ وعند حذف أسطر، تكون بطاقة لا يراها المستخدم أبداً. أما المؤشر فلا يتأثر: «قبل المهمة 3» تعني الشيء نفسه مهما حدث في الأعلى.

What our API doesCe que fait notre APIما الذي تفعله واجهتنا البرمجية

The backend uses Django REST Framework's CursorPagination, ordered by -visited_at with an index on that column. The cursor it returns looks random, but it is only base64: Le backend utilise CursorPagination de Django REST Framework, trié par -visited_at avec un index sur cette colonne. Le curseur qu'il renvoie a l'air aléatoire, mais ce n'est que du base64 :تستعمل الواجهة الخلفية CursorPagination من Django REST Framework، مرتبةً حسب -visited_at مع فهرس على هذا العمود. المؤشر الذي تُرجعه يبدو عشوائياً، لكنه مجرد base64:

next_cursor: cD0yMDI2LTExLTIwKzE3JTNBNTElM0EyOS41NzE1MjYlMkIwMCUzQTAw
decoded:     p=2026-11-20 17:51:29.571526+00:00

SELECT ... FROM missions_mission
WHERE visited_at < '2026-11-20 17:51:29.571526'
ORDER BY visited_at DESC
LIMIT 4      -- page size 3, plus one row to know if there is a next page

p is the position: the date of the last mission on the page. DRF only uses the first ordering field for it; when several rows share that value, it adds an offset to the cursor to skip the ones already shown, capped at 1,000. So the ordering field should be unchanging, indexed and nearly unique. A mission's completion date fits well. p, c'est la position : la date de la dernière mission de la page. DRF n'utilise que le premier champ de tri pour ça ; quand plusieurs lignes ont la même valeur, il ajoute un décalage au curseur pour sauter celles déjà affichées, limité à 1 000. Le champ de tri doit donc être immuable, indexé et presque unique. La date de fin d'une mission convient bien.p هو الموضع: تاريخ آخر مهمة في الصفحة. ولا يستعمل DRF إلا حقل الترتيب الأول لذلك؛ وعندما تتشارك عدة أسطر القيمة نفسها، يضيف إزاحة إلى المؤشر لتخطي ما عُرض منها، بحد أقصى 1,000. لذلك يجب أن يكون حقل الترتيب ثابتاً ومفهرساً وشبه فريد. وتاريخ إنجاز المهمة يناسب ذلك جيداً.

Base64 is not encryption: anyone can read a DRF cursor. That is fine for a date already shown on screen, but a cursor must never carry anything the user should not see. Le base64, ce n'est pas du chiffrement : n'importe qui peut lire un curseur DRF. C'est sans problème pour une date déjà affichée à l'écran, mais un curseur ne doit jamais contenir quelque chose que l'utilisateur ne doit pas voir.base64 ليس تشفيراً: يستطيع أي شخص قراءة مؤشر DRF. وهذا لا يضر بالنسبة لتاريخ معروض أصلاً على الشاشة، لكن يجب ألا يحمل المؤشر أبداً شيئاً لا ينبغي للمستخدم رؤيته.

What the frontend got wrongCe que le frontend faisait malما أخطأت فيه الواجهة الأمامية

The frontend was my part, and rereading it, three things did not match what we claimed: Le frontend, c'était ma partie, et en le relisant, trois choses ne correspondaient pas à ce que nous annoncions :كانت الواجهة الأمامية من نصيبي، وعند إعادة قراءتها، وجدت ثلاثة أشياء لا تطابق ما كنا نعلنه:

  • React Query was installed, not used. The README listed it, but pages, loading and errors were managed by hand with useState and a ref to avoid double requests.React Query était installé, mais pas utilisé. Le README l'annonçait, mais les pages, le chargement et les erreurs étaient gérés à la main avec useState et une ref pour éviter les doubles requêtes.كانت React Query مثبّتة لكن غير مستعملة. كان README يذكرها، لكن الصفحات والتحميل والأخطاء كانت تُدار يدوياً بـ useState ومرجع (ref) لتفادي الطلبات المزدوجة.
  • An artificial delay. Each request waited 800 ms before calling the API, most likely left over from testing the loading state. With pages of 3, reading all 300 missions means 100 requests, so at least 80 seconds of pure waiting.Un délai artificiel. Chaque requête attendait 800 ms avant d'appeler l'API, sans doute un reste des tests de l'état de chargement. Avec des pages de 3, lire les 300 missions, c'est 100 requêtes, donc au moins 80 secondes d'attente pure.تأخير مصطنع. كان كل طلب ينتظر 800 جزء من الألف من الثانية قبل استدعاء الواجهة البرمجية، وهو على الأرجح بقايا اختبار حالة التحميل. وبصفحات من 3، تعني قراءة المهام الـ300 كلها 100 طلب، أي 80 ثانية على الأقل من الانتظار المحض.
  • Virtualization was promised, not built. The README explained that only visible cards are rendered and recycled while scrolling. In reality, after scrolling to the end, all 300 cards were in the page. Pagination limits what you fetch; virtualization limits what you render, and we had only the first.La virtualisation était promise, pas construite. Le README expliquait que seules les cartes visibles sont affichées et recyclées pendant le défilement. En réalité, après avoir défilé jusqu'au bout, les 300 cartes étaient toutes dans la page. La pagination limite ce qu'on télécharge ; la virtualisation limite ce qu'on affiche, et nous n'avions que la première.كان التمثيل الافتراضي (virtualization) موعوداً لا منجزاً. كان README يشرح أن البطاقات المرئية وحدها تُعرض ويُعاد استعمالها أثناء التمرير. لكن في الواقع، بعد التمرير حتى النهاية، كانت البطاقات الـ300 كلها في الصفحة. الترقيم يحدّ مما نجلبه؛ والتمثيل الافتراضي يحدّ مما نعرضه، ولم يكن لدينا إلا الأول.

The hook now uses useInfiniteQuery, which is built exactly for cursor pagination: each page tells React Query where the next one starts. Le hook utilise maintenant useInfiniteQuery, fait exactement pour la pagination par curseur : chaque page indique à React Query où commence la suivante.أصبح الـ hook يستعمل useInfiniteQuery، المصمَّم تحديداً للترقيم بالمؤشر: كل صفحة تخبر React Query من أين تبدأ الصفحة التالية.

const query = useInfiniteQuery({
  queryKey: ['missions'],
  queryFn: ({ pageParam }) => fetchMissions(pageParam),
  initialPageParam: null,
  getNextPageParam: (last) =>
    last.pagination.has_more ? last.pagination.next_cursor : undefined,
});
const missions = query.data?.pages.flatMap((page) => page.data) ?? [];

The 800 ms delay is gone, the README now says that virtualization is not implemented yet, and the seed command no longer crashes on Windows terminals because of an emoji in its output. Scrolling to the end in a browser loads the 300 missions in 100 requests with no duplicates, and React Query sends the first request only once, even under React's strict mode. Le délai de 800 ms a disparu, le README dit maintenant que la virtualisation n'est pas encore implémentée, et la commande de seed ne plante plus dans les terminaux Windows à cause d'un emoji dans son affichage. En défilant jusqu'au bout dans un navigateur, les 300 missions arrivent en 100 requêtes, sans doublon, et React Query n'envoie la première requête qu'une seule fois, même avec le mode strict de React.اختفى تأخير الـ800 جزء من الألف من الثانية، وأصبح README يقول إن التمثيل الافتراضي لم يُنجز بعد، ولم يعد أمر توليد البيانات ينهار في طرفيات ويندوز بسبب رمز تعبيري في مخرجاته. وعند التمرير حتى النهاية في المتصفح، تصل المهام الـ300 في 100 طلب دون تكرار، ولا ترسل React Query الطلب الأول إلا مرة واحدة، حتى مع الوضع الصارم في React.

What a cursor costsCe que coûte un curseurما الذي يكلّفه المؤشر

  • No "jump to page 50": you can only go forward or back from where you are. Fine for a feed or a history, not for a search results page with numbered pages.Pas de « aller à la page 50 » : on ne peut qu'avancer ou reculer depuis là où on est. Très bien pour un fil ou un historique, pas pour des résultats de recherche avec des numéros de page.لا يوجد «انتقل إلى الصفحة 50»: لا يمكنك إلا التقدّم أو الرجوع من حيث أنت. مناسب لموجز أو سجل، لا لصفحة نتائج بحث بأرقام صفحات.
  • The sort order is fixed by the index. Sorting by another column needs its own index and its own cursor.L'ordre de tri est fixé par l'index. Trier par une autre colonne demande son propre index et son propre curseur.ترتيب الفرز يحدده الفهرس. والفرز حسب عمود آخر يحتاج إلى فهرس خاص به ومؤشر خاص به.
  • Page size still matters: pages of 3 made a good demo, but 100 round trips for 300 items is a lot. Something like 20 to 50 is more usual.La taille des pages compte toujours : des pages de 3 faisaient une bonne démo, mais 100 allers-retours pour 300 éléments, c'est beaucoup. Entre 20 et 50, c'est plus courant.حجم الصفحة ما زال مهماً: صفحات من 3 كانت مناسبة للعرض، لكن 100 رحلة ذهاب وإياب لـ300 عنصر كثير. والأكثر شيوعاً شيء بين 20 و50.

TakeawaysÀ retenirالخلاصة

  • OFFSET reads and discards every skipped row: its cost grows with the page number. A cursor with a matching index costs the same on every page.OFFSET lit et jette chaque ligne sautée : son coût grandit avec le numéro de page. Un curseur avec l'index qui va bien coûte la même chose à chaque page.يقرأ OFFSET كل سطر متخطى ثم يرميه: كلفته تكبر مع رقم الصفحة. أما المؤشر مع فهرس مناسب فكلفته نفسها في كل صفحة.
  • Positions move when data changes; values do not. For feeds and histories, page by value.Les positions bougent quand les données changent ; les valeurs, non. Pour les fils et les historiques, paginer par valeur.المواضع تتحرك عندما تتغير البيانات؛ أما القيم فلا. للموجزات والسجلات، رقّم بالقيمة.
  • Order by something unchanging and unique, adding the id as a tie-breaker if needed.Trier par quelque chose d'immuable et d'unique, en ajoutant l'id pour départager si besoin.رتّب حسب شيء ثابت وفريد، مع إضافة id لفك التعادل عند الحاجة.
  • Pagination and virtualization solve different problems. And a README should describe the code that exists.La pagination et la virtualisation règlent des problèmes différents. Et un README doit décrire le code qui existe.الترقيم والتمثيل الافتراضي يحلان مشكلتين مختلفتين. ويجب أن يصف README الشيفرة الموجودة فعلاً.
